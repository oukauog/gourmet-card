## 8. 設計上の判断・迷った点

1. **エラー名**: 依頼には無い独自エラー4種を追加。`NotFoundError` という名前は Dexie と衝突するため `RecordNotFoundError` にした（2章）。今後エラーを増やす時も、DOMException と同じ名前（`NotFoundError`、`ConstraintError`、`DataError`、`AbortError` など）は避けること
2. **インデックス**: 依頼の目安どおり。`rating`・`prefecture`・`city`・`stationId`・`updatedAt` のインデックスは今は使っていないが、絞り込み（工事6）に備えて version 1 で張った（後から足すと version を上げる必要があるため）。rating が undefined の店はインデックスに載らない（IndexedDB の仕様）ので、「未評価のみ」の絞り込みはインデックスではなく全件を読んで判定する想定
3. **ソート**: `listShops` は全件を読んでからメモリ上で並べ替える。数百〜数千店なら問題ない。名前順は `Intl.Collator('ja')` を使うため、漢字の並びは読みではなく文字コード順に近くなる（読みで並べるにはフリガナ項目が必要。今は仕様外）。同順位の並びを毎回同じにするため、同順位は新しい順（さらに同じなら id 順）にした
4. **ISO 文字列の採用**: 賛成です。`toISOString()` は常に同じ桁数・UTC で出るので、文字列のまま比較しても時刻順と一致します。ただし工事8の取り込みで、他の形式（タイムゾーン付きなど）が入ると比較が崩れるので、取り込み時に `toISOString()` 形式へ正規化するのが安全です
5. **ratingFromNumber は四捨五入しない**: 3.75 のような 0.1 刻みでない値は、丸めずに RangeError にした（知らない間に値が変わるのを防ぐため）。スライダー等で 0.1 刻みの値を渡す限り問題ない。丸めて受け付ける方が良ければ変更します
6. **updateShop の範囲**: photoIds は写真 API（addPhoto / removePhoto / reorderPhotos）でだけ変えられる。タグ配列は編集画面でまとめて保存できるように patch でも受け付けるが、存在と種別を検証する。`undefined` は「未設定に戻す」、空白だけの文字列も「未設定」として保存
7. **createShop では id・日時を指定できない**: 自分で登録する店には十分ですが、工事8の取り込み（バックアップ復元・お裾分け）では元の id と日時を保ったまま保存する必要があります。取り込み用の関数は工事8で別に作る想定です（下記 質問2）
8. **タグの表示名**: trim だけして、入力した表記のまま保存（内側の空白はまとめない）。suggestTags の並びは正規化キーの文字コード順（読み順ではない）
9. **DB の単一インスタンス**: リポジトリ関数はすべて `db` を使う。テストは毎回 `db.delete()` → `open()` で空の状態から始める（`testHelpers.ts` の `resetDbAndClock`）。別名の DB が要るテストは `createDb(name)` を使う
10. **時計と ID の差し替え**: `setClock()` で時計を差し替えられる。テストでは呼ぶたびに1秒進む時計を使い、作成順と updatedAt の変化を決定的に確認している
11. **改行コードの警告**: 書き換え（rebase）の後、作業ツリーの一部のファイル（`.gitignore`、`CLAUDE.md` など）が CRLF になっていて、コミット時に Git の警告が出ます。リポジトリ内の中身は LF で、動作や差分には影響しません

## 4. ZIP の作り（`src/lib/zipStore.ts`）

### 書き出し `buildZip(entries, 日時, 進み具合)`
- 各項目は「名前」と「中身を出す関数 `load()`」で渡す。`load()` は**その項目の番が来た時にだけ**呼ばれる
- 各項目は次の順で処理する
  1. 中身（写真は DB の Blob）を1つ読み、CRC-32 を計算する。計算に使ったバイト列はすぐ手放す
  2. ローカルヘッダ（30 バイト＋名前）の ArrayBuffer と、**中身の Blob そのもの**を部品の列に足す
- 最後に、セントラルディレクトリと End of Central Directory を足して `new Blob([...部品])` にする
  - 全部を1つの ArrayBuffer にはしない。IndexedDB の写真の Blob は、そのまま並べるだけ
  - メモリに載るのは「今 CRC を計算している1枚」だけ
- 方式は STORE のみ。フラグ 0（データディスクリプタなし）、暗号化なし、ZIP64 なし
- 4 GB を超える／65,535 項目を超える時は `ZipFormatError`
- ZIP の中のファイル名は ASCII だけ（違えば `ZipFormatError`）。名前の重複も `ZipFormatError`
- 日時は書き出し日時（端末の現地時刻の DOS 形式）

### 読み込み `openZip(file)`
- ファイル末尾の最大 22＋65,535 バイトだけを読み、End of Central Directory を後ろから探す
  - 見つからない・分割 ZIP・ZIP64 の印・中央ディレクトリがはみ出す → `ZipFormatError`
- セントラルディレクトリだけを `blob.slice()` で読み、名前・CRC・大きさ・位置の表を作る
  - STORE 以外（DEFLATE 等）・暗号化・圧縮後と元の大きさが違う項目があれば `ZipFormatError`
  - フォルダの項目（名前が `/` で終わる）は無視する
- 項目は**要る時に1つずつ** `blob.slice()` で切り出す
  - ローカルヘッダで中身の開始位置を確かめる
  - 切り出したバイト列の CRC-32 を確かめ、合わなければ `ZipCrcError`
- 取り込みは店1つ分の写真（最大3枚×大小）ずつ読む（6章）

### JSZip との相互確認（`zipStore.test.ts`）
- 自作で作った ZIP を JSZip が普通に読める（空の項目・日本語 JSON・バイナリ）
- JSZip が STORE で作った ZIP（フォルダの項目つき）を自作で読める
- JSZip が DEFLATE で作った ZIP は `ZipFormatError` で断る
- ほかのテスト
  - 往復（中身のバイト列一致）、空の ZIP、項目が1つずつ順に読まれること
  - ASCII でない名前・重複した名前、DOS 日時
  - 1バイト壊した写真だけが CRC エラーになる（ほかの項目は読める）
  - ZIP でない・JPEG・末尾が切れたファイル（10 バイト／半分）

## 6. 取り込みの規則とその実装（`src/db/importCards.ts`）

### 下見 `previewCard(file)`（拡張子は見ない）
- 手順
  1. `openZip` できない → 「グルメカードのファイルではありません」
  2. `manifest.json` が無い、または `format` が違う → 同じ文言
  3. `formatVersion` が 1 より大きい → 「新しい版のアプリで作られたファイルです。アプリを新しくしてから取り込んでください」（取り込まない）
  4. `shops.json`・`tags.json`・`photos.json` が無い／JSON でない → 「ファイルが壊れているため読めませんでした」
- **店ごとの検証**（`readShop`）。おかしい店は、その店だけ飛ばして `skippedShops` に数える
  - 店名（空白を除いて空でない。前後の空白は外す）
  - status・origin は決まった値
  - rating は 1〜50 の整数か無し
  - 写真は3枚まで（重複は1つに）
  - タグ id は文字列の配列
  - 任意の文字列項目は文字列（空白だけなら未設定）
  - 日時は `Date.parse` できれば ISO（UTC）に正規化、できなければ飛ばす
  - 知らない項目は捨てる
  - 同じ id の店がファイルの中に2件あれば、2件目を飛ばす
- タグは `readTag` で検証する（正規化キーはファイルを信用せず名前から作り直す）
- 写真
  - `photos.json` にその店の写真として載っていて、大小の両方が ZIP にある写真だけを残す
  - 無い写真は外して `skippedPhotos` に数える
  - 写真 id は ZIP の中の名前に使うので、英数字と `-` `_` だけ（UUID）に限る
- タグ id は、ファイルのタグにあって種別が合うものだけ残す
- 「新しいお店」「もう入っているお店」は、端末に同じ `id` があるかで分ける

### 保存 `importCard(下見, { overwrite })`
- **1店ずつ Dexie のトランザクション**（shops・photos・tags を含める）
  - 途中で失敗しても、それまでに入った店は残る
  - 失敗した店は `failed` に数え、次の店へ進む
- **写真**
  - トランザクションの**前に**その店の写真（最大3枚×大小）を読み、CRC を確かめる
    - IndexedDB のトランザクションの中では、ほかの待ちを挟めないため
  - CRC が合わない写真は外して `skippedPhotos` に数える（店は入れる）
  - 1枚ずつ読んだバイト列から `new Blob([bytes], { type: 'image/jpeg' })` を作って保存する（ファイルの切り出しのままにしない）
  - ファイルの id・width・height・createdAt を保つ
  - 同じ id の写真が端末の**別の店**にある時だけ、新しい id を振る（`photoIds` も新しい id で並べる）
- **お裾分け（share）**
  - `status: 'wishlist'`、`origin: 'shared'`、`createdAt`・`updatedAt` は取り込んだ日時
  - id・名前・評価・メモ・場所・駅・URL・写真・タグはそのまま
- **バックアップ（backup）**: id・日時・status・origin を含め全部そのまま
- **同じ id の店**
  - 既定は取り込まない（`keptExisting` に数え、店にも写真にも触らない）
  - 「上書きする」の時は、その店の今の写真を全部消してから、届いた内容で置き換える（share なら上の変換の後）
- **タグ**（店より先に、1つのトランザクションで）
  - 同じ種別＋正規化キーのタグが端末にあれば、それに合流する（表示名は端末のまま）
  - 無ければ作る。ファイルの id が端末で空いていればその id、空いていなければ新しい id。作成日時はファイルのまま
  - 店のタグ id は、合流先・新しい id へ付け替える
  - バックアップは、ファイルの全タグ（店に付いていないものも）を同じ規則で入れる
  - お裾分けは、取り込む店に付いているタグだけ（取り込まない店のタグは作らない）
- **駅 id**: 駅マスタに無くても、そのまま保存する（テストに「駅がマスタに無い店」を入れて往復を確認）
- 取り込み後は一覧の記憶（`HomeScreen` のモジュール変数）を消す
  - 次に一覧を開くと読み直す（e2e で「一覧を見た後に取り込む → 新しい件数が出る」を確認）
  - タグ候補・絞り込みの候補は、もともと DB やこの一覧から毎回作るので、新しいタグ・店を含む
- **取り込んだ後の行き先**
  - 1店なら「お店を見る」→ その店ページ
  - 複数なら「一覧を見る」→ お裾分けは「行きたい」タブ、バックアップは「手札」タブで、条件なし・先頭で開く（`resetListView(tab)`）
  - どちらも「閉じる」でこの画面に残れる

## 7. 共有とダウンロード（`SendSheet.tsx`・`shareFile.ts`）

- 「この店を送る」「全店のバックアップを作る」を押すと、シートが出て**準備だけ**を始める
  - 表示は「準備しています… 写真 12/60」
  - 準備ができたら「準備できました（1.9MB）」とファイル名を出す
- **「共有メニューを開く」**
  - `navigator.canShare({ files: [file] })` が true の時だけ出す
  - 押すと `navigator.share({ files: [file] })` を呼ぶ（title・text なし）
  - **準備の押下と同じ流れでは呼ばない**（必ず2回目の押下）。e2e で、準備の後も `share` が呼ばれていないことを確認
  - 成功すると「送りました」を出し、1.2 秒で閉じる
  - `AbortError`（共有メニューを閉じた）の時は、何も言わずシートに戻る
  - その他のエラーの時は「共有できませんでした。「ファイルとして保存」をお試しください」とエラー名を小さく出す
- **「ファイルとして保存」**
  - 常に出す
  - 押した操作の中で `<a download>`＋object URL を実行する（URL は 30 秒後に解放）
- **最後のバックアップ**
  - 全店の時だけ、共有の成功か「ファイルとして保存」で `settings.lastBackupAt` を記録する
  - 共有メニューを閉じただけ（AbortError）・1店を送った時は記録しない（e2e で確認）
- 準備したファイルはシートを閉じると手放す（object URL は保存の時にだけ作る）

## 12. 設計上の判断・迷った点

1. **写真の説明（`photos.json`）の作り方**
   - 書き出し時に写真のレコードを1件ずつ読んで、幅・高さ・日時だけを取り出しています
   - IndexedDB から読んだ写真の Blob は中身の参照だけで、バイト列が載るのは ZIP を組み立てる時の1枚ずつです
2. **CRC の不一致は取り込む時に分かる**
   - 下見では全写真を読まないため、確認画面の「読めない写真」には「ファイルに無い写真」だけが出ます
   - CRC が合わない写真は、結果の「読めない写真 N枚」に出ます
3. **お裾分けの日時は1店ずつの取り込み時刻**
   - 工事8b で複数店をまとめて送る時は、店ごとに少しずつ違う時刻になります
   - 並びは取り込んだ順（ファイルの順）の新しい順です
4. **「上書きする」の時の日時**: お裾分けなら取り込んだ日時、バックアップならファイルの日時です（規則どおり）
5. **タグの作成日時**: 新しい id を振った時も、ファイルの作成日時を保ちました
6. **取り込み中はシートを閉じられない**ようにしました（途中で画面を離れて状態が分からなくなるのを防ぐため）
7. **lint の警告は2か所で止め（理由を書いたコメントつき）、1か所は書き方を直した**
   - `HomeScreen.tsx` の `resetListView`: 一覧の記憶（モジュール変数）の隣に置く必要があるため
   - `FileTypeTrial.tsx` の `currentCardFileType`: 試験用の切替は工事8aでファイルごと消すため、1ファイルにまとめたため
   - どちらも React の開発時の即時反映（Fast Refresh）が効きにくくなるだけで、動きには影響しません
   - `DataScreen` の effect 内の読み込みは、警告が出ない形に直しました
8. **ZIP の日時**: 端末の現地時刻（DOS 形式にはタイムゾーンが無いため）。取り込みでは使いません
9. **メニューボタン**: 今は「バックアップと取り込み」だけなので、押すとすぐその画面を開きます（メニューの一覧は出さない）。工事10でタグ整理が増えたら、この画面に並べる想定です
10. **一覧の上部バー**: 390px 幅で、題名・列数ボタン・メニューボタンが1行に収まります（`01-list-menu.png`）

## 17. 保留・質問

1. **iPhone のメモリ**
   - 書き出しは写真を1枚ずつ読みますが、最後にできる ZIP の Blob（例 42MB）を `File` にして共有メニューへ渡すところは、ブラウザの作りに任せています
   - 写真の多いバックアップで Safari が落ちないかは、実機で見てください（15章4）
2. **共有メニューで「"ファイル"に保存」以外（LINE 等）へ大きなバックアップを送った場合**: 相手側の容量制限は相手のアプリ次第です
3. **`.gcard` の MIME `application/octet-stream`**: iPhone の共有メニューで「"ファイル"に保存」が出るか、LINE が受け付けるかが、工事8a の判断材料になります
4. **取り込み時のファイル選択**
   - `accept` を付けていないので、写真なども選べてしまいます
   - 選んだ時は「グルメカードのファイルではありません」と出ます
5. 登録画面の保存失敗時の診断表示（仮）は、引き続き残しています

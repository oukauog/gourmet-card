## 4. 画像処理の実装

| 項目 | 内容 |
|---|---|
| デコード経路 | **主経路**は `<img>` と `URL.createObjectURL`（`onload` を待つ）。失敗した時だけ `createImageBitmap(file, { imageOrientation: 'from-image' })` を試す。どちらも失敗したら `ImageProcessError` |
| 向き | 自分で EXIF を読んで回転する処理は**書いていない**。`<img>` がデコード時に向きを適用し、`naturalWidth/naturalHeight` も回転後の値になる前提で、その寸法をもとに縮小して canvas に描くだけ |
| 縮小 | 「大」も「小」も元画像から直接作る（大から小を作り直さない）。canvas は**目標サイズ（最大 1800px）で作る**（元画像サイズの canvas は作らない）。`imageSmoothingQuality = 'high'`。描く前に canvas を白で塗る（透過部分が黒くならないように）。使い終わった canvas は幅・高さを 0 にしてメモリを解放する |
| JPEG 品質 | 小 0.80、大 0.85（`canvas.toBlob('image/jpeg', q)`） |
| 拡大しない | 元が目標より小さければ、同じ寸法のまま JPEG にするだけ |
| 後始末 | `<img>` 用の object URL はデコード・描画の後に必ず revoke する（失敗した時も） |
| 失敗時 | デコード失敗・`toBlob` が null・canvas が取れない場合は `ImageProcessError`（`userMessage` = 「この写真は読み込めませんでした」）。その枡に文言を出し、他の写真の処理と保存は続けられる（失敗した写真は保存されず、3枚の枠にも数えない） |
| HEIC | 特別な対処は書いていない（依頼どおり）。PC の Chrome は HEIC を読めないので、**PC では確認できていない**。iPhone で確認が必要 |

**PC の Chrome（Playwright の Chromium 153、390×844）で fixture を処理した結果**（IndexedDB から読み戻して測定）:

| fixture | 元 | 大（寸法 / サイズ） | 小（寸法 / サイズ） |
|---|---|---|---|
| landscape-3000x2000.jpg | 3000×2000 JPEG、56 KB | 1800×1200 / 27.9 KB | 400×267 / 4.3 KB |
| portrait-800x1200.png（左半分が透過） | 800×1200 PNG、30 KB | 800×1200（拡大なし）/ 12.3 KB | 267×400 / 3.9 KB |
| exif-orient6-2000x1500.jpg（Orientation=6） | 保存上は 2000×1500 JPEG、35 KB | **1350×1800**（縦長）/ 32.2 KB | 300×400 / 4.6 KB |

- fixture は単色の4分割の図柄なので、ファイルサイズがかなり小さく出ています。実際の料理写真（iPhone 12MP）では、大が数百 KB、小が数十 KB になる見込みです（要実機確認）
- 依頼文では EXIF の写真の大を「1200×1600 相当」としていました。今回の fixture は 2000×1500 → 回転して 1500×2000 → 長辺を 1800 にするので、**1350×1800 が正しい値**です（縦長になっていることが確認の要点）

## 6. 設計上の判断・迷った点

1. **トランザクションの入れ子は効いた。ただし親に `tags` も入れる必要があった**
   - 依頼文の例 `db.transaction('rw', db.shops, db.photos, …)` のままだと、`createShop` が内部で `tags` を使うため `SubTransactionError: Table tags not included in parent transaction.` で失敗しました（実際に試して確認）
   - 親を `shops, photos, tags` にしたら、正常に動きました。途中で失敗した時（4枚目・不正な写真・空の店名）は、**店も写真も残らない**ことを単体テストで確認しています
   - 「店だけ残る可能性」は無くなったので、保留事項にはしていません
2. **写真は1枚ずつ処理する**: 複数枚を選んでも、デコードは同時に1枚だけ（iPhone のメモリ対策）。処理を待っている写真も「処理中…」と表示する。画面を離れた後に処理が終わっても結果は捨て、画面は更新しない
3. **object URL の管理**
   - 画像の表示はすべて `BlobImage` に集め、表示する Blob が変わった時と画面から外れた時に revoke する
   - 最初は `useState` で URL を持っていましたが、lint が「effect の中での setState」を警告したので、`<img>` に直接 src を入れる形にしました（React の開発モード（StrictMode）で effect が2回走っても、URL が壊れないことを確認済み）
   - 処理用の `<img>` の URL は `image.ts` の中で revoke する
4. **保存ボタンは `position: fixed` で画面下部に固定した**
   - 下側の余白に `env(safe-area-inset-bottom)` を足してある
   - 入力欄の下にボタンの高さ分の余白を取り、内容がボタンに隠れないようにしている
   - iPhone の Safari では、キーボードを出した時に固定ボタンの位置が動く可能性があります（要実機確認）
5. **写真が満杯の時の「写真を追加」ボタン**: 押せなくする（無効化）と、利用者は理由が分かりません。そこで、ボタンは押せるままにし、押すと「写真は3枚までです」を出すようにしました。一度に4枚以上選んだ時も、先頭の3枚まで受け付けて同じ文言を出します
6. **表紙ラベル**: 「保存される写真のうち先頭」に付けます（先頭の枡が失敗や処理中の時は、次の完了済みの写真に付く）
7. **仮ホームのサムネイル**: `getPhotosForShop` の先頭と同じ写真ですが、`getPhoto(shop.photoIds[0])` で表紙1枚だけを取っています（大きい画像を余計に読まないため）
8. **隠した input を `click()` で開く方式**: 依頼どおりに作りました。iOS Safari でも利用者がタップした流れの中の `click()` なら選択画面が開く想定ですが、実機で確認が必要です。開かなければ、`<label>` で input を包む方式に切り替えます（すぐ直せます）
9. **その他の小さな判断**
   - 店名欄で改行キー（done）を押すと、保存できる状態なら保存する（フォームの送信扱い）
   - ×ボタンが白い写真の上でも見えるよう、×の後ろに半透明の黒丸を敷いた
   - e2e で `page.evaluate` の中でブラウザの API を使うため、`register.spec.ts` の先頭に `/// <reference lib="dom" />` を書いた（tsconfig は変えていない）
10. **新規ファイルを `src/db/` に置いた件**: `createShopWithPhotos.ts` は DB を扱う処理なので `src/db/` に置きました。既存ファイルは変更していません。画面側に置く方が良ければ移します
11. **ビルドサイズ**: 328 kB（gzip 105 kB）。今のところ問題はありません。工事9（PWA 化）でキャッシュされます
